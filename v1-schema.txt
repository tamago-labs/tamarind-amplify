Updated Schema Plan

V1 will include the complete workflow schema, including execution and invoice approval models. We will not implement the frontend or execution logic yet.

The schema must support:

Multiple payment connections per Workflow

Payment and invoice flows

Drag-and-drop canvas nodes

Template references

Payment execution

Counter-party invoice approval

Settlement and Merkle proof references

Identity Mapping

Tamarind does not need separate DepositWallet or RecipientWallet models.

Both are represented by WorkspaceIdentity.

OrganizationIdentity
  -> Company wallet

WorkspaceIdentity
  -> Counter-party wallet
  -> Payment recipient
  -> Invoice deposit/payer

The same WorkspaceIdentity can be used as:

Payment recipient

Invoice payer

Invoice deposit source

The Company should be able to view the approval state, but the Counter-party is the approver in v1.

Template Integration

Each connection references a template:

templateId
templateVersion

Payment templates are used for:

Company -> Counter-party

Invoice templates are used for:

Counter-party deposit -> Company

The selected version must be stored on WorkflowConnection and copied to WorkflowRun.

This ensures a completed payment always knows which document template version was used.

Settlement and Proof Integration

After a payment settles:

WorkflowRun
  -> settlementId
  -> Merkle root
  -> TamarindProof

A single settlement maps to one Merkle root.

A receivable can reference multiple settlement proofs:

Receivable
├── settlementId A -> Merkle root A
├── settlementId B -> Merkle root B
└── settlementId C -> Merkle root C

Indexes

The schema should support these query patterns:

Workflow by workspaceId
WorkflowNode by workflowId
WorkflowConnection by workflowId
WorkflowRun by workflowId
WorkflowRun by connectionId
InvoiceApproval by workflowRunId

These indexes are important for loading a canvas and its execution history without scanning the entire workspace.

Published Workflow Behavior

Published workflows should be treated as immutable from the application perspective.

To change a published workflow:

Duplicate published workflow
  -> create new version
  -> edit draft
  -> publish new version

The schema should retain:

version
status
publishedAt

The frontend and future backend operations will enforce the editing behavior.

Future Payment Flow Integration

Templates are only configuration for now.

Later, a payment flow will reference:

templateId
templateVersion

For a payment:

Payment flow
  -> selects Payment template
  -> fills sender/recipient/amount/chain/txHash
  -> generates document
  -> hashes document
  -> links hash to settlement
  -> anchors proof through TamarindProof

For an invoice:

Invoice flow
  -> creates invoice document
  -> sends invoice to recipient
  -> recipient approves
  -> payment is sent
  -> template is rendered with approval/payment data
  -> final document hash is created

No rendering or document generation needs to be implemented in this template milestone.

Recommended Implementation Sequence

Add DocumentTemplate to Amplify Data.

Scope templates by workspaceId.

Add payment, invoice, and payslip document types.

Add controlled field catalog constants.

Port the Goji template list page.

Add draft and publish status.

Add template versioning.

Add archive instead of delete.

Later connect templates to payment and invoice flows.
